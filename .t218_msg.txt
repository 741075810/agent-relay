T218: the extension files are in the directory Chrome loads, verified there, and Chrome has not been asked to reload

The operator authorised the extension upgrade. The mistake this round had to avoid was telling him to press Reload on the
*old* files: the reload must land on the new build, so the new build goes into the directory Chrome already loads, gets
verified there, and only then is he asked to act.

**Where it actually loads, from Chrome's own record.** `Secure Preferences` names the path, `location: 4`
(`LOAD_UNPACKED`), and the granted APIs (`alarms`, `nativeMessaging`, `storage`, `tabs`, `scripting`) with host access to
`chatgpt.com` and `chat.openai.com`. The manifest carries no `key`, so the id is a consequence of the path: sha256 of the
**UTF-16LE** path string, first 32 hex digits mapped onto `a`..`p`. `extension_identity.py` recomputes it and compares it
with Chrome's record (`agrees=True`). That is why the files were written into that directory: a copy elsewhere would have
minted a different id and orphaned the manifest's `allowed_origins`, the host's allow-list and Chrome's stored grants.

**What was written.** Fifteen files, in place: `background.js`, `popup.js`, `popup.html`, `lib/terminal_trigger.js`
(55,524 → 59,772 B, `postArmUsable` present), `lib/autosend.js`, `lib/autosend_chrome_wiring.js`, `lib/send_adapter.js`,
`lib/build_stamp.js`, plus seven new modules (`terminal_events.js`, the three `diagnostic_*`, `notice_runtime_view.js`,
`readiness_queue_view.js`, `run_history_view.js`). `manifest.json` was **not** touched — it is byte-identical (`89FF5835…`),
so permissions and identity cannot have moved. Nothing was deleted; every replaced file's previous bytes are in the T217
backup, re-verified this round (43 entries, 0 problems, and its extension tree differs from the install by zero files).
